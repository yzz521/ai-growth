# 13｜架构决策记录（ADR）

## ADR-001：MVP 使用 FastAPI + SQLite + 原生 Web UI

决策：首版不立即建设 Java/Vue 完整工程。原因：个人开发、闭环验证优先，减少构建和部署复杂度。后果：不适合直接作为公网 SaaS；付费验证后迁移 Java/Vue/PostgreSQL。

## ADR-002：微信采用用户主动采集

决策：不读取微信内部数据库、不注入进程、不静默全量聊天。原因：稳定性、账号安全和个人信息保护。后果：首版无微信全量同步，依靠剪藏、文件导入和本地助手。

## ADR-003：多平台先人工发布

决策：统一生成、编辑、审核和人工发布记录；官方 API 按平台授权逐一接入。原因：平台能力和权限不同，不依赖模拟登录。后果：首版不是全自动发布工具。

## ADR-004：模型采用兼容 API 适配器

决策：环境变量配置 OpenAI Chat Completions 兼容模型。原因：避免单一厂商耦合。后果：特殊协议需另写适配器；远程调用涉及数据处理和服务商政策。

## ADR-005：知识修改保留版本

决策：每次更新插入新版本，不覆盖历史。原因：知识需要溯源，价格、政策和客户信息可能冲突。后果：存储增长，需要保留策略。

## ADR-006：MVP 不做多 Agent 自由协作

决策：先提供边界清楚的业务服务和少量 AI 任务。原因：降低幻觉、成本和调试难度。后续按真实场景引入 LangGraph、白名单工具和人工审批。
